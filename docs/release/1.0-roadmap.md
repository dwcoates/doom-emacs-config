# Release roadmap: 0.9 and the path to 1.0

Status: investigation, 2026-10-13. D1 and D2's ground is decided (see 1.4);
every other "Decision" below waits on the owner.

Paths are relative to the repository root. `R` = `modules/app/agent-repl`.

---

## 1. What "0.9" means here

### 1.1 Current state

- **No tags, no release.** `git tag` lists only stray `start/*`, `temp-*` and
  `wip-*` refs. 14k commits on master.
- **Builds carry a git identity, not a version.**
  - Daemon: `R/daemon/cmd/agent-repld/graph.go:1042` reads `.built-sha` into
    `agentrepl.v1.DaemonIdentity.build_sha`
    (`R/proto/src/agentrepl/v1/endpoint_daemon_health.proto:40-48`).
  - Shim: `R/bin/build-frontend.sh` passes `SHIM_BUILD_SHA` to
    `R/agent-shim/claude/shim/build.mjs:64`, read at runtime by
    `src/build-identity.ts`.
  - Webapp: `.build-id` is the Vite entry-bundle hash
    (`R/bin/build-frontend.sh:584-606`), used as a cache key, not an identity.
  - Store / sidecar (Go, launchd): built by hand per
    `R/launchd/AGENTS.md`, no stamp at all.
- **Placeholder package versions.** `R/webapp/package.json` (`claude-repl-webapp`
  `0.1.0`), `R/agent-shim/claude/shim/package.json` (`0.1.0`). Go modules use
  bare paths (`module agent-repld`), not importable URLs.
- **A changelog-like file exists but is a fix log.**
  `R/docs/REMEDIATION-CHANGELOG.md` is one line per landed remediation, for
  regression watch. Not user-facing.

### 1.2 Proposal: 0.9 is four things

1. **One source of truth: a `VERSION` file** (plain `0.9.0`, SemVer) at the
   product root (`R/VERSION` now; the new repo's root after extraction).
   - Chosen over a git tag as the source because builds run from dirty
     worktrees and from staging slots (`build-frontend.sh --out`) where
     `git describe` lies or is absent. The tag is *derived from* the file at
     release time and must match it (a test enforces this, see 4).
2. **Every component reports `VERSION` + build sha at runtime.**
   - `bin/build-frontend.sh` (already the single build entrypoint) reads
     `VERSION` once and passes it beside the sha it already computes:
     - Go (daemon, store, sidecar): `-ldflags "-X <pkg>/buildinfo.Version=…
       -X …Sha=…"` into one shared `buildinfo` package under
       `R/proto/helpers/go` (all three already depend on it). The store and
       sidecar builds move into `build-frontend.sh` (or its successor) so
       none is built by hand.
     - Shim: `SHIM_BUILD_VERSION` beside `SHIM_BUILD_SHA` in `build.mjs`'s
       `define`.
     - Webapp: Vite `define: { __AGENT_REPL_VERSION__ }`.
     - Elisp: `agent-repl-version` constant generated from `VERSION` (or read
       from the file at load time; the module ships with its source).
   - Proto: add `string version = 4` to `agentrepl.v1.DaemonIdentity`; the
     shim's health/hello answer gets the same field. The editor and webapp
     compare their own version to the daemon's and show a typed fault on
     mismatch (this is the first time a version skew is *detectable*).
   - `agent-repld --version` and `M-x agent-repl-version` print
     `0.9.0 (<sha>)`.
   - `package.json` versions are set from `VERSION` by the build (or a
     `bin/set-version.sh` the release step runs), never by hand.
3. **A user-facing `CHANGELOG.md`** (Keep a Changelog format) at the product
   root. 0.9.0's entry is a feature summary, not a replay of 14k commits.
   `REMEDIATION-CHANGELOG.md` stays as the internal fix log.
4. **An annotated tag `v0.9.0`** cut on master *through the merge queue's
   landing commit*, plus a unit test (`bin/test-version.sh`) asserting
   `VERSION` parses as SemVer, every `package.json` matches it, and
   `CHANGELOG.md` has an entry for it.

### 1.3 Decisions

- D1. `VERSION` file as the source (recommended) vs. the git tag as the source.
- D2. Does the version skew between editor/webapp and daemon become a hard
  fault (recommended, typed `DaemonFault` arm) or only a displayed value?
- D3. Is 0.9 cut *before* the rename (tag `v0.9.0` on `doom-emacs-config`) or
  is the rename part of 0.9?

### 1.4 Decided (owner, 2026-10-13)

- **The version lives in git tags, bare `MAJOR.MINOR.PATCH`, no `v` prefix.**
  The seed is the annotated tag `0.0.1`. This supersedes the `VERSION` file
  proposed in 1.2 (D1).
- **The merge queue moves the version on every merge onto agent-repl's
  master.** An agent's merge names `minor` or `patch` and a one-line changelog
  entry; the queue tags the landed merge commit with the next version,
  annotated with that line, so the changelog is read from the tags. The
  daemon refuses an agent's merge onto master without an increment, and any
  other merge with one. Breaking changes are minor increments.
- **Only a human moves the major version**, by tagging master by hand, as a
  judgment of maturity rather than a marker of breaking change.
- **The merge bubble's head shows the landed version**, the incremented
  number in green.
- Contract and design record:
  `modules/app/agent-repl/docs/protobuf-design/merge-version-increment.md`.
- Still open from 1.2: reporting the version at runtime from each component
  (`git describe` at build time instead of a `VERSION` file) and D2.

## 2. The 1.0 targets

### 2.1 Real names (repository and product)

**Current.** Repository `github.com/dwcoates/doom-emacs-config`; the README
calls it "Personal Doom Emacs configuration". The product is `agent-repl`
everywhere: elisp prefix `agent-repl-`, daemon `agent-repld`, launchd labels
`com.agentrepl.*` (`R/launchd/`), proto package `agentrepl.v1`, state under
`~/.cache/agent-repl`, logs `~/.claude-emacs/logs/agent-repl-*`. Webapp is
still named `claude-repl-webapp`.

**Gaps.** A rename is a wide but mechanical change: elisp symbol prefix
(thousands of symbols), proto package names (wire-breaking; must ride a
`v1`→ new package, landed as a contract change on an integration branch),
launchd labels, on-disk paths (need a one-time migration of the store and
state dirs), skills (`R/skills/*`), and every doc.

**Decisions.**
- D4. Product name. Constraints worth applying: unclaimed on MELPA / npm /
  GitHub, short elisp prefix, not tied to one vendor (the shim layout
  `R/agent-shim/claude/` already anticipates other backends). Candidates to
  react to (not vetted for collisions):
  - **`atelier`** (a workshop of workspaces)
  - **`warren`** (many burrows, one system)
  - **`switchyard`** (workspaces, merges, a queue)
  - **`conclave`**
  - **`benchwork`**
- D5. Repository naming after the split (2.5): product repo takes the product
  name; the Doom config stays `doom-emacs-config` (or `dotdoom`) as a
  consumer.
- D6. Whether the elisp prefix is the full name or a short alias (e.g.
  `swy-`); Emacs convention favors the full package name.
- D7. Rename before or after extraction (recommended: extract first, rename
  in the new repo so history stays legible).

### 2.2 Real, robust user documentation

**Current.** `R/docs/USER-GUIDE.md` (402 lines) is a list of feature notes
(merge bubble, rollback, effort, zoom, sidebar search…) plus a Setup section.
It assumes the reader already runs it under Doom+evil (`SPC o …`, `SPC TAB …`).
The rest of `R/docs/` and the `R/design-*.md`, `R/test-coverage-*.md`,
`docs/overhaul/` trees are developer/internal records, not user docs.
`R/skills/agent-repl-help` answers questions from these docs.

**Gaps.**
- No concepts chapter (workspace, session, feed, footer, merge queue,
  sidecar/store) for a first-time reader.
- No install guide independent of `/install-agent-repl` and
  `bin/requirements.sh`.
- No key reference table generated from the keymaps (it would drift by hand).
- No troubleshooting index beyond two sections.
- Internal docs sit beside user docs; a reader cannot tell them apart.

**Proposal.** A `docs/` tree split into `user/` (getting started, concepts,
guides per feature, key reference generated from the keymaps by a script with
a test, troubleshooting, FAQ) and `dev/` (architecture, protocols, logging
contract, testing). Internal dated reports move to `dev/records/` or out of
the product repo.

**Decisions.**
- D8. Doc format: Markdown on GitHub (recommended, already the norm) vs. a
  site (mkdocs) vs. an Info manual (Emacs-native, expected for MELPA
  packages). Possibly Markdown plus an Info export.
- D9. Do the dated internal records (`docs/overhaul/`, `R/docs/investigations`,
  audits, `REALTEST-*`) ship in the public product repo?

### 2.3 Emacs (non-evil) keybindings

**Current.**
- Every leader binding goes through Doom's `map! :leader`
  (`R/lisp/keybindings.el:99-160`, 336 lines); a no-op `map!` shim exists
  only so batch byte-compile passes (`keybindings.el:19-21`).
- Evil state appears in 8 non-test sources (`keybindings.el`, `input.el`,
  `frontend.el`, `magit.el`, `core.el`, `panels.el`, `popup.el`,
  `clipboard-image.el`).
- The module is loaded from the root `config.el` via
  `doom-after-modules-config-hook` precisely so it wins over evil-bindings
  (`init.el:196-199`), and `M-1..9` workspace switching is also wired from the
  root `config.el:395-402`.
- Some keymaps are already plain data (`keybindings.el:167-200`, "a keymap of
  our own"), which is the right foundation.

**Gaps.** No prefix keymap usable without a leader; composer keys in
`input.el` assume evil insert/normal states.

**Proposal.** One plain `agent-repl-command-map` (prefix keymap) holding every
command, defined with `define-keymap`/`keymap-set` and no Doom or evil
dependency. Then thin adapters:
- vanilla: user binds the prefix (suggested default `C-c a`), composer uses
  standard Emacs editing keys.
- evil/Doom: the current leader layout is one `map!` binding the same
  prefix map to `SPC o`/`SPC TAB`/`SPC j`, plus evil state tweaks, loaded
  only when `evil` is present (`with-eval-after-load 'evil`).
A test asserts the evil layout and the vanilla prefix name the same commands
(no command reachable from one only).

**Decisions.**
- D10. Default vanilla prefix (`C-c a` is reserved-for-users by convention;
  packages may only suggest it).
- D11. Is the leader layout a separate key tree from the vanilla one, or the
  same tree under a different root (recommended: same tree).

### 2.4 A full, robust README

**Current.** `README.md` (50 lines) describes the Doom config; agent-repl gets
one line. There is no product README; `R/AGENTS.md` is the de-facto overview
but is agent-facing.

**Gaps.** What it is, a screenshot/GIF, requirements (macOS, Emacs with
xwidgets, Go, Node, Claude Code), install, first run, keybindings for both
styles, architecture diagram, license, status/compat matrix, contributing.

**Decision.** Mostly blocked on D4 (name) and 2.5 (which repo it lives in).

### 2.5 Standalone library (Doom module, or another host)

**Current.**
- Already well separated by process: daemon (Go), shim (TS), sidecar/store
  (Go, launchd), webapp (TS), elisp client — all under `R/` with their own
  `go.mod`/`package.json`. 4274 of the repo's 4503 tracked files are under
  `R/`.
- Elisp client is coupled to Doom: persp-mode / Doom workspaces (`persp-*`,
  `doom-real-buffer-list`, `doom-fallback-buffer`, hundreds of references),
  `map!`, Doom popup rules in the root `config.el:224-229`.
- The webapp already speaks to the daemon directly over HTTP/connect
  (`R/webapp/src/main.ts:109`, `createDaemonTransport(window.location.origin)`)
  and has a "host page" (`R/webapp/src/host/main.ts`) that Emacs drives via
  `window.agentReplHost` (`R/lisp/webhost.el`). xwidget focus details are
  NS-port specific.
- The daemon's API is protobuf: ~80 endpoints in `R/proto/src/agentrepl/v1`,
  15 render messages in `R/proto/src/frontend/v1`. Several are editor-shaped:
  `endpoint_open_in_editor`, `endpoint_report_editor_focus`,
  `endpoint_adopt_host_workspace`, `endpoint_open_tabs`.
- macOS-only: launchd services (`R/launchd/*.plist`,
  `R/daemon/internal/deploy/launchctl.go`), Homebrew-based requirements
  (`R/requirements.json`), `*_darwin.go` paths, Emacs NS xwidgets.

**Gaps toward "any host".** A non-Emacs host needs from the daemon:
1. A documented, versioned **host contract**: which endpoints a host must
   implement callbacks for (open file at line, focus reports, tab
   ownership) vs. which it only calls. Today these are implied by
   `lisp/wire-*.el`.
2. A **host capability handshake** (host declares: can open files, has a
   tab bar, can show notifications) so the daemon stops assuming Emacs.
3. **Workspace ownership that is not persp-mode**: the daemon already owns
   the roster; the elisp persp binding should become one adapter.
4. A **transport the host can reach**: unix socket + HTTP today; document
   it, and the auth model (currently "same user, local socket").
5. **Service management** that is not launchd-only (systemd user units, or
   the daemon supervising store/sidecar itself).

**Proposal: repository shape.**
- Extract `R/` into its own repository with history
  (`git filter-repo --subdirectory-filter modules/app/agent-repl`), laid out
  as: `daemon/`, `shim/`, `store/`, `sidecar/`, `proto/`, `webapp/`,
  `clients/emacs/` (the elisp package, MELPA-shaped, no Doom requirement),
  `clients/doom/` (a thin Doom module: `packages.el` pulling the package,
  `config.el` with `map!` leader bindings and persp integration).
- The Doom config then consumes it as a normal package (`package!` with a
  `:recipe` pointing at the repo), not a subtree.
- Go module paths become importable (`github.com/<owner>/<name>/daemon`).

**Decisions.**
- D12. Separate repository (recommended) vs. `git subtree` inside the Doom
  config vs. monorepo with the Doom config moved out. Separate repo is the
  only option that lets a non-Doom user install it.
- D13. Library boundary: is persp-mode a hard dependency of the Emacs client,
  an optional integration (recommended: optional; daemon owns workspaces),
  or replaced by `tab-bar`?
- D14. Is "another host" a 1.0 deliverable (a working second host, e.g. a
  browser page served by the daemon, which the webapp nearly is) or a 1.0
  *contract* (documented host API, second host after)?
- D15. Platform scope for 1.0: macOS only (honest, current), or macOS + Linux.
- D16. Backend scope: Claude Code only, or is the "pluggable backends: claude
  code, codex" claim in the README a 1.0 promise.

## 3. Other 1.0 blockers found

### 3.1 Licensing
- **No `LICENSE` anywhere.** Without one the code is all-rights-reserved and
  cannot be used by anyone. Decision D17: license (MIT / Apache-2.0 / GPL-3.0;
  GPL-3.0 is conventional for Emacs packages and required for GNU ELPA;
  MELPA accepts any free license). Third-party notices for bundled
  dependencies (webapp bundles, vendored chess widget if any) need checking.
- Contributor terms (DCO or none) if others will contribute.

### 3.2 Install story
- Today: `.claude/install.sh`, `/install-agent-repl`, `R/bin/requirements.sh`
  with manifest `R/requirements.json`. Thorough, but driven through Claude
  Code skills and Homebrew, and builds everything from source on the user's
  machine.
- 1.0 needs a non-agent path: either prebuilt release binaries per platform
  (GitHub Releases from a CI release workflow, keyed to the tag) plus a
  package for the elisp, or a documented `make install`. Decision D18:
  ship prebuilt binaries (recommended) vs. build-from-source only.
- Emacs with xwidgets is a hard requirement on macOS; the install doc must
  name a supported Emacs build.

### 3.3 Hardcoded personal values and accounts
- `bin/check-personal-values.mjs` passes clean for the module (home dir,
  emails), so paths are in good shape.
- Remaining **account-specific default**: `~/.claude-chesscom` is the default
  of `agent-repl-daemon-multi-repo-config-dir` (`R/lisp/daemon.el:230`) and
  of the sidecar's `--config-roots`
  (`R/agent-shim/claude/shim-sidecar/main.go:127`), plus
  `R/agent-shim/claude/shim/scripts/capture/capture.mjs:662`. These must
  become configuration with no employer-specific default.
- Employer-specific features: the chess board widget / `show_chess_board`
  MCP tool and CEE skills (`R/skills/show-chess-game`). Decision D19: do
  they ship in the product, move to an optional plugin, or stay in the
  personal config.
- Repo-root files tracked that should not ship (or exist):
  `.claude-repl-history` (268 KB of prompt history), `.agents-sandbox/`,
  `.claude/sandbox/sandbox.log`. They stay behind on extraction but should
  also be untracked here.

### 3.4 Secrets
- `git grep` for Anthropic/GitHub/AWS/Slack token shapes finds only test
  vectors in `anonymize.test.mjs`. No tracked secrets found in the tree.
- **History not scanned.** Before publishing, run a history scanner
  (`gitleaks detect` over all commits); recorded captures under
  `R/agent-shim/claude/shim/testdata/captures/` are scrubbed by the capture
  tooling but older commits may predate the scrub. Extraction via
  `filter-repo` is the moment to drop anything found.

### 3.5 Tests that assume the owner's machine
- Many test and harness scripts assume macOS, launchd, Emacs.app, and
  `~/.claude*` layouts (`R/bin/realtest.sh` drives the real Emacs.app;
  `R/bin/test-e2e-emacs.sh`). Realtests are by design local; they must be
  marked as such and excluded from a public CI.
- No public CI yet that runs unit + integration on a clean runner. A clean
  macOS runner (and Linux if D15 says so) is the real test of "no
  assumptions"; expect fallout there.
- `R/test_time.csv`, `R/testrun/`, coverage reports are working records
  at the module root and should move under `dev/`.

### 3.6 Repository hygiene for a public product
- ~40 root-level `R/*.md` design and coverage docs; move to `docs/dev`.
- `metaprompt.md`, `AGENTS.md`, `CLAUDE.md`, `R/skills/` are agent-facing;
  decide which are part of the product (skills such as
  `manage-agent-repl-runtime` plausibly are) and which are personal process.
- Stray refs (`start/*`, `temp-drop-merge-queue`, `wip-message-lineage`) to
  prune before the first tag.

## 4. Proposed sequence

1. **0.9.0** (in this repo): `VERSION`, build plumbing and the
   `DaemonIdentity.version` field, `--version`, CHANGELOG, version test, tag.
2. **Decouple inside the repo**: plain command keymap + evil/Doom adapter
   (2.3); persp-mode as an optional adapter (D13); the `~/.claude-chesscom`
   default to config (3.3); store/sidecar built by `build-frontend.sh`.
3. **License + history scan** (3.1, 3.4).
4. **Extract** to the new repository (2.5), rename (2.1), importable Go
   module paths, Doom config consumes it as a package.
5. **Docs + README** in the new repo (2.2, 2.4), key reference generated.
6. **Release machinery**: CI on clean runners, prebuilt binaries, `v1.0.0`.
