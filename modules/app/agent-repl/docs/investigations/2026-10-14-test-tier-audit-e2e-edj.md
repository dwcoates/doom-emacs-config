# Test tier audit, e2e half (Option B): which e2e tests need e2e

Workspace `test-tier-audit-e2e-edj`, child of `agent-repl-test-slimming`, 2026-10-14. An INVESTIGATION: no test was deleted, moved or merged. Every proposal below is **semantically judged and unconfirmed**. It becomes confirmed only when test-redundancy-measure's mutation tool shows that the remaining tests kill every mutant the proposed removal kills. That tool was not on master when this report was written.

## Scope

- **The e2e Go package (`e2e/`, package `.`).** It has 354 top-level Test funcs and 38 `t.Run` sites. Both suites run it:
  - `e2e` runs the package on the host;
  - `e2e-emacs` runs its `TestEmacs*` subset inside the Docker sandbox.
- **Not audited: `e2e/realtest` (296 funcs).** It is behind `//go:build realtest`, so neither suite runs it; testrun only vets it. The brief's "~648" count included it.
- **Two files hold no Test funcs:** `precondition_test.go` and `landing_test.go` are harness code with a `_test.go` suffix.
- **366 audit rows.** Most rows are one top-level test; a subtest gets its own row where it checks something different.

## Method

- Six read-only agents each audited one file group. They read every test body, its helpers and the lower-tier suites, then ruled per row:
  - **KEEP**: the assertion needs several real systems together. The row names the seam.
  - **MOVE**: one system's logic. The row names the target tier, the package and the existing covering test, or says "new test needed".
  - **DELETE**: the same assertion already exists elsewhere, named in the row, so nothing needs writing.
  - **MOVE-HARNESS**: the test checks the e2e harness, not the product.
- The lead spot-checked covering-test claims against the source, and all of them held:
  - `TestAMergeOfABranchThatDoesNotExistIsRefused` makes the same `unknown_branch` assertion as `daemon/integration/merge_sources_test.go` "a branch that does not exist".
  - `TestMonitorRowJumpsToTheMonitorsToolCallCard` matches `daemon/integration/footer_topbar_test.go:TestFooterMonitorRowJumpsToTheMonitorsToolCallCard`.
  - `TestEmacsLauncherRefusesWithoutAnAccountRoot` is covered by `lisp/test-daemon.el` `agent-repl-test-daemon-empty-default-config-dir-refuses-the-launch` and `daemon/integration/boot_test.go:TestBootRefusesWithoutAnAccountRoot`.
  - The webapp layer's proof-of-life is repeated exactly by `client-log.layer.test.ts`'s `beforeAll`, which submits a prompt and waits for the same `echo:` row.
- **Timing source.** Per-test times are `~/.cache/agent-repl/test-history.json` `item:e2e:.:<Test>` means (hundreds of samples each).
  - Each value is a test's wall time inside a chunk that overlaps 8 tests on one core (`roster.go`: `TestParallel {".": 8}`). The sum is therefore a test-time total, not CPU.
  - `TestEmacs*` rows show the host suite's preflight wait. Those tests skip on the host and really run in `e2e-emacs`, whose history holds only a whole-suite figure: `unit:e2e-emacs` 130s wall on 2 slots.

## Estimated e2e runtime saved

Two different measures, labelled each time they appear:

- **History seconds.** The `test-history.json` item means: each test's WALL time inside a full run, with 8 tests overlapping per chunk on one loaded core. They rank tests against each other, but they are inflated well past cost. test-shared-setup measured about 16x for median daemon integration tests.
- **CPU seconds.** rusage user+sys of each chunk's whole process tree (test binary, daemons, shims, node, store, sidecar), as testrun prints it per unit. Source: the e2e-only run of 2026-10-14 19:57 (`testrun run --suites e2e`, branch `repl-merge-racing-toggle`, 13 chunks):
  - the chunks used 27.9-40.6 CPU-seconds each, about 430 CPU-seconds in all;
  - the whole run reported 435.8 CPU-seconds and 118s wall on 13 slots;
  - vet and build together used under 5 CPU-seconds, since the build is mostly cached.
  - Caveat: that run was not green. Five tests failed on bounded waits (`TestPushNotificationNotSent`, `TestHookFailed`, `TestASuccessorThatFinishedJoiningAcceptsADeploy`, `TestInterruptAfterTextDelta`, `TestVendorBackgroundedTaskStartIsNoDetachment`), and their chunks paid those waits in full. Waiting burns little CPU, but treat about 430 as an upper bound.
- testrun records CPU per chunk, not per test. The per-ruling CPU figures below therefore split the 430 CPU-seconds in proportion to each test's history seconds. That split is an approximation, and it is labelled as one.
- **No solo-second figures.** Measuring them would mean running the e2e tests one by one, which this investigation did not do (battery, shared suite slot). test-redundancy-measure's per-test runs can supply them.

## The scenario-matrix change (ruling 1, drafted for the implementation)

### The problem the change has to solve

- Today a matrix row counts as covered only when an e2e file submits the scenario's prompt (`scenariomatrix_test.go`, check (iv)).
- Under ruling (a), a row is covered by a shim half plus a daemon half. But daemon tests never name a vendor scenario: they push frames through `daemon/integration/fakeshim` (`push_agent_frame`, `push_session_update`).
- So "this daemon test proves scenario X's daemon half" cannot be derived from a literal the way the e2e columns are. A hand-written annotation would be an unchecked claim, which is exactly how the matrix lied before it was derived.
- The two halves must be bound by something both of them read. Otherwise the shim half can prove one stream while the daemon half proves a different, hand-written one.

### The design: one per-scenario frame fixture that both halves read

1. **The fixture is the contract between the halves.**
   - `testdata/scenario-frames/<scenario>.json` sits at the module root, beside the shared `testdata/`, so neither system's suite depends on the other's source.
   - It holds the canonical protojson of what the real shim emits for the scenario on its stream plane: WatchAgent frames and session updates, with ids and times normalized.
   - Its header names the scenario's `seam` family, for example `stream-tool-card`, `turn-failure` or `two-plane-episode`.
2. **The shim half: one vitest table**, `agent-shim/claude/shim/test/integration/scenario-frames.test.ts`.
   - It drives every scenario `fake/registry.ts` registers through a real shim with the fake SDK, the way `turn.test.ts` does, and compares the output to the committed fixture.
   - A missing fixture fails, and so does a stale one. `AGENT_REPL_SCENARIO_FRAMES_WRITE=1` regenerates them, the same convention as the matrix's own `AGENT_REPL_MATRIX_WRITE`.
   - Result: a fixture is exactly what the shim emits. This is structural; the fixture cannot drift from the shim.
3. **The daemon half: one table** in the cheapest daemon tier that can project frames.
   - The target is `daemon/internal/resolve/feed` (unit) wherever the resolver accepts the entries directly, and `daemon/integration` with fakeshim only where the projection needs the session's wiring.
   - It loads EVERY fixture in the directory, feeds it through, and asserts the projected rows and terminal against `scenarioExpectations`, a map keyed by scenario name.
   - A fixture with no expectation fails, and so does an expectation with no fixture. So every shim half has a daemon half, or the daemon suite is red. That is structural too.
4. **Scenarios whose daemon-visible result needs the sidecar's file plane**, such as detached shells and subagent transcripts:
   - their fixture header says `planes: stream+file`;
   - their seam family is a two-plane family, which by the tier rule has its one e2e wiring test.
   - The sidecar's own half stays in its integration suite, as today.
5. **Changes to `e2e/scenariomatrix_test.go`:**
   - Two new derived columns. `Shim half`: the fixture file exists. `Daemon half`: the scenario's key is present in `scenarioExpectations`, read with `go/parser` from the composite literal's keys, the technique `goFieldLiterals` already uses.
   - A new derived `Seam` column, taken from the fixture header. A new check that every seam family named by a fixture has at least one e2e test whose doc comment carries `Seam: <family>`, read with `go/parser` (plus the `.layer.test.ts` scan for the webapp layer). The reverse check: every `Seam:` comment names a family that exists.
   - Check (iv) is redefined so that `covered` or `weak` requires shim half AND daemon half AND a wired seam, and `uncovered` is anything else.
     - The three e2e columns stay derived and stay exact; check (iii) is unchanged.
     - The e2e columns become informational: they no longer decide the verdict.
   - Section (b) gains count lines for the two halves and for seam families. `matrixLayerCount` and `checkMatrixCounts` are extended to match.
   - In `SCENARIO-MATRIX.md`, "Counted layers are Go, webapp and Emacs ... daemon/integration, shim test/integration and sidecar integration tests do NOT count" is replaced by the (a) definition, citing the 2026-10-14 ruling.
6. **Order of landing, so that no commit leaves a scenario uncovered:**
   - first the fixtures, the shim table and the daemon table, which only add coverage;
   - then the matrix change;
   - then the e2e deletions, one area per commit, each confirmed by the mutation tool.
- What the draft does not settle: the shim table's runtime over about 150 scenarios. Each scenario costs one `spawnShim` with the fake SDK and no daemon, store or sidecar. It must be measured before it lands.

## The Doom tier (ruling 2, design sketch)

### What it must see that no current tier sees

- Doom's `map!` bindings, the leader map included. In batch `emacs -Q`, `keybindings.el` compiles `map!` to a no-op.
- Doom's popup rules (`set-popup-rule!` into `display-buffer-alist`) and where a buffer actually lands.
- Doom's workspace recycling (persp-mode).
- It does NOT need a real daemon, shim, store, sidecar or vendor. The fake daemon (`lisp/testsupport/fakedaemon`) already speaks `agentrepl.v1` with the strict codec, and the ERT integration suites drive it.

### How Doom boots in it

- **Recommended: the existing e2e sandbox image, a GUI frame on Xvfb, the image's real Doom profile.** The boot mechanism is exactly `e2e-emacs`'s (`EMACS-LAYER-SPEC.md`, "It boots real Doom"):
  - `HOME` is staged from the image's `EMACSDIR`;
  - the `sandbox/doom/` profile is used;
  - the one readiness stamp is written from Doom's after-init edge.
- **Daemonless.** The fake daemon starts first, on the test's state root, and writes `daemon.addr`. Emacs's ensure then takes the adoption path for an already-answering daemon (`test-integration-daemon.el` `daemon-answering-daemon-is-adopted`), so no launcher, no `agent-repld` build and no shim are ever spawned.
- **Rejected: running against the host's own Doom.** It would reach the developer's `~/.config/doom` and `~/.emacs.d`, which is the reason the Emacs layer is sandboxed at all.
- **Considered, unverified: a batch Emacs that loads Doom's core** (noninteractive, the way the `doom` CLI loads it). It would skip Xvfb, but three obstacles stand in the way:
  - the spec's reasons against batch still hold for popups: no window system, no redisplay, no tab-bar;
  - `config.el` gates cold start on `(not noninteractive)`;
  - persp-mode behavior in batch is unknown.
  - First step if pursued: measure whether `map!` lookups and `display-buffer-alist` resolution are faithful in a Doom-loaded batch Emacs. Until that is measured, the GUI frame is the design.

### Cost per process

- Measured today (`testrun/roster/roster.go`, 2026-10-12): the worst Doom boot inside the sandbox is 0.88s on 2 CPUs, against its 3.5s bound.
- An `e2e-emacs` scenario costs about 4.4 slot-seconds. That includes the real daemon's spawn and its first link, and for turn scenarios the shim, store and sidecar.
- The Doom tier pays Xvfb plus the Doom boot plus a fake-daemon start (a Go binary built once per run, like the ERT suites' `AGENT_REPL_ITEST_FAKEDAEMON` prebuild). The container start is shared by the whole suite.
- This is unmeasured; the first implementation step measures one case end to end.

### Sharing one boot across cases

- **Recommended: one Emacs per test FILE, with cases as ERT tests inside it.** That is the convention every existing ERT suite already follows (`lisp/test-integration-*.el`: one Emacs per file, fake-daemon state reset between tests through `/_fake/reset`).
  - Files would be `lisp/test-doom-<module>.el`, one per source module (the module's one-test-file-per-source rule), run inside the booted Doom by the suite script.
  - Each test's fixture resets the module's state and the fake daemon, the same discipline as `test-integration-helpers.el`.
- **Not recommended: one booted Emacs shared by every file.** That is the "sharing mutable state across tests to save setup" which `skills/write-tests/SKILL.md` refuses. It is also test-shared-setup's question (Option C), not this tier's.
- At about 6 cases today, per-file booting costs a few seconds in total, so sharing more buys nothing.

### Where it runs

- A new roster suite, for example `emacs-doom`, run by a script beside `bin/test-e2e-emacs.sh` in the same container image. It declines with exit 77 when the sandbox is unusable, exactly as `e2e-emacs` does.
- It is an Emacs INTEGRATION tier (one real system, Emacs, plus the fake daemon), so it follows the integration rule, not the e2e one. It sits under `lisp/`, not `e2e/`.
- Until it exists, the ~6 rows stay in `e2e-emacs`, per the ruling.

### 3. Notes

#### Why the webapp layer costs ~264s of reported test time

1. **The per-test seconds are mostly queueing, not work.** Every area takes one of two `wlAreaSlots` (webapplayer_e2e_test.go:891) before building its world, and then `wlServer.Run` (webapplayer_server_test.go) holds a mutex: the warm driver runs exactly one area file at a time. A Go test's reported duration therefore includes waiting for the other slot-holder's whole vitest run. The measured child walls in the file's own comments are 1.8-8s per area (cold) and the driver comment says 22s of a 169s cold total was tests; the 12-39s figures in the inventory are dominated by waiting.
2. **The warm driver's warm-up (17s idle, 26s loaded; `wlWarmupBound`) is charged to whichever area first calls `wlLayerServer`**, under `wlServerMu`, so the first area or two absorb it.
3. **Real turns are the intrinsic cost.** feed-families drives ~24 real turns through one page (the longest area by work), subfeeds 6, surfaces 3+, cards 10 asks. Each is a real shim turn plus settle loops in jsdom. Moving the rendering assertions to the fake-daemon tier removes those turns entirely, which is the biggest saving available.
4. **Two areas bypass the warm driver and pay a cold vitest each:** TestWebappLayerRestartHandover (wlStartVitest, its 16.7s is largely the cold npm/node/vite transform, ~17s by the driver's own warm-up figure) and TestPerfWebappLayer. The handover one cannot use the request/answer driver as written because the Go side must act while the page is mounted; the driver would need a concurrent-request mode (Run releases its lock while the Go side acts) to share warmth.
5. **Not browser launches.** jsdom, no real browser. Per area the costs are world build (~2-3s: store, sidecar, daemon, shim) plus the file's real turns plus queueing.

**Would a shared-setup change help?** Some, but the larger win is MOVE. Ideas in order of value:
- Apply the MOVE/DELETE rulings: if only ClientLog (with proof-of-life folded in) and RestartHandover remain, the layer drops from 12 areas to 2, roughly 230s of reported time and about 9 world builds, and the cap/serialization question mostly disappears.
- If more areas are kept: lower `wlMaxConcurrentAreas` from 2 to 1. Since the driver serializes runs anyway, a second slot only lets one more world sit idle, its processes using resources and its own context clock running, while it waits on the mutex. That is the load the slot comment says the cap exists to prevent.
- Several areas could share one world on separate workspaces (one daemon, N registered repos), since each area's subject is one workspace. The spec's ruling 4 (one world per area) is what forbids this; it is an owner call.

#### Surprising or miscategorized findings

- **Dead code:** `wlRunVitest` (webapplayer_e2e_test.go:831) has no callers since the warm driver landed. `wlChild.Wait` is reached only from it.
- **The layer's two production findings are not pinned by any test.** WEBAPP-LAYER-SPEC.md §G findings 1 (usage stamp never populated) and 2 (SetModel on a served option fails at the transport) sit in comments only. Finding 2 is a real page<->daemon contract fault, the one kind of thing only this layer can see, and refusals.layer.test.ts deliberately asserts around it. If the layer is cut down, finding 2 needs its own assertion. Best home is a Go e2e or daemon/integration SetModel test with a served option. If it is a transport/CORS/route issue only a browser fetch hits, it would be the one more reason to keep a G1-world case.
- **roster.layer.test.ts drain case:** the comment says the daemon fires a schedule set for `Date.now()+1h` immediately, and the case waits on the restarting notice because of that. That reads like a daemon defect (or a clock mismatch), not a harness artifact. Worth a look whichever way the case is ruled.
- **TestWlKillTreeReapsAGrandchild and wlAwaitPidFile poll with `time.Sleep(pollInterval)`.** That is the pattern the owner's rules forbid for synchronization. The grandchild's death has no channel to wait on, so a poll may be the only option, but it is a second group-kill implementation (H1) that could be deleted outright.
- **TestWebappLayerParticipantHoldOutlivesTheWaitBound** still names the hold's bound as WebappLayerTimeout. Since 2026-10-13 the hold is released by its holder (context.WithCancel in wlDriveAreaWorld), not a clock, so the first subtest's rationale is partly stale. It still pins a true relation between constants.
- **Spec drift:** WEBAPP-LAYER-SPEC.md §F counts (66 tests, nine areas) and §E's `WebappLayerTimeout` 10s row are stale against the code (12 areas, 45s bound plus the 20s silence bound on the warm driver). The cards file has 10 cases, the spec says 9.
- The perf_* files never run in the functional e2e suite (`//go:build perf`), so they contribute 0s to the ~745s. Ruling them changes nothing for e2e runtime.

### Notes

- **Stale integration comment, possible coverage gap.** daemon/integration/prompt_test.go:TestInterruptAllAgentsStopsEveryLiveDetachedAgent says "interruptAllAgents sweeps AGENTS only". internal/workspace/interrupt.go:interruptAllAgents checks `LiveWork.Shells` too, and TestFanWideCancel asserts count 3 including the shell. The shell arm of the all_agents stop has no integration test; one should be added before TestFanWideCancel could ever move.
- **TestFanWideCancel is misfiled** in mergequeue_e2e_test.go (its own comment admits it has no merge involved).
- **Conflicting warning declarations, same act.** TestAStopAfterACompletedTurnLeavesOnTheStop asserts no WARN in any system's log. TestACompletedTurnAndTeardownLeaveNoWatchTokenOutstanding performs the identical turn plus stop but declares about 14 daemon warning operations (kill_session, link_fault, …). Either the declarations are stale or ExpectWarnings only permits rather than requires. It is worth checking which, and dropping stale declarations so they cannot mask a real regression.
- **Not parallel.** TestAStopAfterACompletedTurnLeavesOnTheStop has no t.Parallel. The three TestColdGate subtests have no t.Parallel either, so their roughly 6.6s runs serially; parallel subtests would cut wall time to about 2.2s if the cold gate stays.
- **Degraded tests are the slowest here** (5.85s and 7.36s) for a reason unrelated to their assertion. Their waits are bounded by StoreOutageWindow, and the time goes on the shim noticing the store loss and reconnecting. Deleting the prefix test saves about 5.9s outright. The shim's reconnect backoff under --fake may deserve a measured, tighter setting.
- **Self-repo merge worlds are costly.** Every mqSelfRepoWorld or adSelfRepoWorld landing also waits on AwaitLandingDeployed, a full deploy handover. That is why MQ-tabs, FailMarker/after-self and Coalesce/self-repo each cost about 2 to 2.4s for one daemon-composed assertion.
- **Headless "handover" tests** (deploy free-workspace, deploy successor, adoption freeness) register a workspace that is never opened, so no shim takes part in the handover. In adoption, the only real-shim activity is the trigger child's initial turn, which is incidental.
- **TestDisplacedTurnCapturedEndedThenResubmittedExactlyOnce** (3.01s, three daemons) re-proves the exactly-once bookkeeping already pinned twice in daemon/integration/merge_test.go. It could be cut to the cross-process facts (interrupted terminal from the real shim, the adopted shim serving the resubmission) and lose the third bounce and the probe-window wait, which by design always waits out harness.ProbeWindow.

### Notes

- **Why failurearms costs ~42s.** TestApiRequestFailedArms (16.85s) and TestTerminalReasonTurnFailedArms (15.10s) are table tests whose 12 and 10 parallel subtests each build a full NewWorld: a store process, a sidecar process, a daemon process, a node shim spawn, a fake-git repo registration and a durable sidecar cursor wait. That is 22 complete stacks to check 22 rows of what amounts to a lookup table. The cheapest world in this group is ~0.7s (TestStartSessionVendorStartFailed) and a single-turn world is ~0.85-1.3s. The parent's reported time is the wall time of all its subtests contending for the -parallel slots and CPU. The assertions are pure mapping facts already table-tested on both sides (shim-taxonomy, d-turnended, d-words), so this is the largest single saving in the group. If any rows are kept, one World with N workspaces (or N sequential turns in one workspace) would avoid N-1 stack boots.
- **Why keepalive costs ~20s.** TestStopReplayedByEveryRewindNeverLoops (11.63s) runs 6 subtests that each build an identical world and repeat the same arrangement: arm `!stop-on-rewind`, await 3 stop replays and 3 keep-alive rewinds at the 100ms compressed cadence, then a real prompt. Only the final assertion differs, so one world could run all six checks, saving ~5 world boots and ~5 replay chains (~9-10s). TestRestartedShimCarries… (2.26s) chains two shim lifecycles through RestartWorkspace. The other four tests each wait several 100ms beats on top of a world boot. Almost all of this is shim-internal (reads only the shim log), and shim-int turn.test.ts already holds most of these exact claims.
- **Serial keep-alive tests.** In hibernation_e2e_test.go, TestKeepAliveNeverAppearsOnWire, TestKeepAliveAnswerAfterVendorTurnNeverServed, TestKeepAliveStoresNothingOnEitherPlane and TestPromptDuringKeepAliveTurnsOnce do NOT call t.Parallel(). They run serially before the parallel batch, adding ~3.6s of wall time. I found no comment explaining why. If they stay at e2e, either add t.Parallel or record the reason.
- **SCENARIO-MATRIX consequence.** The matrix counts only Go e2e, webapp-layer and Emacs e2e as coverage (owner ruling: daemon/integration and shim/sidecar integration do NOT count), and TestScenarioMatrixMatchesReality enforces that a `covered`/`weak` row has an e2e driver. Moving the failurearms / turnlifecycle / producerfaults rows down will flip many `!api-*`, `!fail-*`, `!query-*`, residue and usage rows to `uncovered` and fail that check until the matrix is regenerated. The matrix's coverage definition (or that ruling) has to change alongside any MOVE here. This needs an owner decision, not an agent's.
- **Expected-fail test.** TestModelRefusalWithoutFallback's doc says "WRITTEN TO THE PROTO, EXPECTED TO FAIL". The daemon now has a refusal producer (d-turnended:TestAModelErrorAfterARefusedResponseDrawsTheRefusalArm), but shim-int turn.test.ts records that `!refusal-no-fallback` publishes no AgentResponseFailure.reason on the stream plane. So it is either red or passing through a path I could not confirm without running it. Either way, the precise home for the defect is a shim test.

## Group D: tools, detached work, subagents, session facts, permissions, questions, hooks, MCP and monitors, skills, slash commands

Scope: e2e/{detachedbash,detachedlost,subagents,sessionfacts,filetools,webtools,permission,questions,hooks,mcpmonitors,skills,slashcommands}_e2e_test.go.

How these tests work. Almost every test here submits a `!scenario` prompt, so the real shim runs its fake SDK, converts the vendor records to conversation.v1, and sends them over WatchAgent/WatchSession/WatchBash to the real daemon. The test then asserts on a frontend.v1 row, footer or topbar that the daemon projects. Each half of that path already has thorough tests at a lower tier:
- Shim half: `agent-shim/claude/shim/test/convert/tools/*.test.ts` (per tool), `test/convert/hooks.test.ts`, `test/fake/scenarios/*.test.ts` (each scenario's vendor records), and `test/integration/{gate,detached,session,turn}.test.ts`. The integration tests run the real shim process with the fake SDK over its real transport, and they drive the same `!perm-*`, `!ask-*`, `!bash-detach*` and `!vendor-backgrounded` scenarios.
- Daemon half: `daemon/internal/resolve/feed/*_test.go` (1192 unit tests), `resolve/footer`, `resolve/topbar`, `resolve/sidebar`, plus `daemon/integration` with the scriptable `fakeshim` (push_agent_frame, push_bash, file_agent_frame, set_live_work, expect UpdateAgent).
- File-plane half (detached spools and transcripts): `agent-shim/claude/shim-sidecar/integration/*` (lost_policy, lost_wire, spool_exit_marker, skill_join, subagent_join, agent_spool_lost) and `shim-store/integration`.

So the question for each test is whether its assertion depends on anything beyond the conversation.v1 contract that both halves are already pinned to. Mostly it does not. What is left at this tier is one wiring test per distinct transport: stream plane, shell spool plane, sidecar LOST relay, subagent sub-stream, detached-agent transcript, transcript-plane join, the answer verb, the stop-detached verb, and session_update.

### 3. Notes

#### Ruling on sandbox_build_lock_test.go (10 tests, 45.77 s summed; about 18.5 s wall, since every test is t.Parallel)

- **What it is.** It tests two bash scripts, e2e/sandbox/bin/e2e-sandbox.sh (the build lock, the source stamp, the stale-image refusal, the CPU cap) and bin/test-e2e-emacs.sh (it hands the slot width to the sandbox). It uses a fake `docker` and bin/fake-git.sh. It imports nothing from the e2e harness: fakeDocker, sandboxScript, fakeGitScript and reapedPid are all file-local. It needs neither the e2e package nor the e2e Go module. Today it pays the e2e module build, TestMain's grep gate, the 6-program prebuild the e2e roster entry demands, and an e2e slot, all to run bash.
- **Natural home.** A bin/test-e2e-sandbox.sh harness suite in testrun/roster (Kind Script, Harness: true), the way every other script in this module is tested (bin/test-e2e-repeat.sh, bin/test-build-frontend.sh, ...). The Harness flag is also the merge gate's blast radius for script changes, so an edit to e2e-sandbox.sh would then gate on the fast harness instead of only on the full e2e suite. A Go test in a tiny module (for example e2e/sandbox/scripttest with no dependencies) is an acceptable second choice if Go's process control is wanted for the live-lock wait test. Either way the lock does not need to "live in a package": it lives in the script, and the script is what gets tested.
- **Why it is slow, per test.**
  - TestSandboxRunAllowsAStaleImageWhenOverridden (18.46 s): after the stamp gate passes, do_run keeps going. It runs the real preflight.sh, then acquire_slot on the host-shared /tmp/agent-repl-e2e-sandbox.slots (the test sets no AGENT_REPL_SANDBOX_SLOT_DIR), then `webapp-dist.sh ensure`. That last step builds the webapp dist in the checkout through build-frontend.sh whenever dist is stale. So the test is slow, and it also breaks isolation in two ways. First, it can queue behind a real e2e-emacs run holding the host slot, which testrun may schedule concurrently, so the 18 s mean likely includes slot waits and webapp builds. Second, it mutates the checkout's webapp/dist. Fix: assert the gate alone. Evaluate the require_fresh_image section by itself, the way currentSandboxStamp and containerCPUArgs already evaluate their sections, or at least set AGENT_REPL_SANDBOX_NO_WEBAPP_BUILD=1, a private AGENT_REPL_SANDBOX_SLOT_DIR and a stub preflight. Expected cost: under 0.5 s.
  - TestSandboxBuildLabelsImageWithTheSandboxStamp (7.5 s) and ...ForceRebuilds... (6.06 s): every build that gets past the skip runs stage_context, which tars every .go file in the module (over a thousand) plus all go.mod/go.sum files into a temp context, then runs verify_image against the fake docker. The assertions only look at the `build` argv. Fix: run do_build with stage_context stubbed (section-eval with a no-op stage_context), or point repo_root at a tiny fake module. Expected cost: under 0.5 s each.
  - TestSandboxBuildWaitsForALockHeldByALivePid (6.89 s): about 2 s is the script's own `sleep 2` lock poll, and the rest is the full stage after release. Stubbing the stage gets it to about 2 s. Making the poll interval an env knob would bring it under 0.5 s. The poll itself is a polling wait in production code; the structural alternative is `flock` on the lock path, which waits in the kernel. That is a design question for the owner, not ruled here.
  - The 1.7 to 2.2 s tests (Skips, RefusesStale, RefusesUnlabelled): two bash spawns each (the stamp is computed by the script plus the script run) with fake-git and shasum over 11 files, measured under the e2e suite's parallel load. They should be well under 1 s on their own.
- **Projected cost after the fixes:** about 3 to 5 s summed, about 1 to 2 s wall, outside the e2e suite. Coverage is unchanged, because the same script paths stay asserted.

#### Should each harness test run inside e2e?

- **Not inside e2e: 17 tests, 49.21 s.** H1 (14 script tests, 48.33 s) and H3 (3 matrix tests, 0.88 s) need neither the e2e package nor the prebuilt binaries. They should leave the e2e suite. That is the only harness move with a real runtime payoff, and almost all of it is sandbox_build_lock.
- **Need package e2e: 47 tests, 0.91 s summed.** H2 (40 tests) and H4 (7 tests) test unexported harness helpers. Inside e2e their marginal cost is about 0, because the build and prebuild are paid for the real tests anyway. Moving them saves no e2e seconds. It only buys faster feedback on harness edits, and only after the helpers are extracted into their own package. That extraction is a refactor, and I would not prioritize it for runtime. One sub-case is worth doing: storedump's stand-in store re-execs the e2e test binary through TestMain, which ties it to the package more tightly than the rest.
- **H4, emacs_teardown (7 tests):** the "TestEmacs" name prefix routes them into the Docker e2e-emacs suite (`go test -run 'TestEmacs'` in bin/test-e2e-emacs.sh). They need Linux /proc and never a real Emacs. On the macOS host they skip, so the sandbox is today the only place they run. Renaming them away from the prefix would silently stop them from running. Leave them until a Linux harness lane exists. Their real cost sits inside the e2e-emacs suite's ~130 s and is not broken out in the inventory.
- **coverage_test.go:** the test is a DELETE-CANDIDATE (the harness's own tests pin both halves). The coverageEnv helper itself stays.

### Notes

- **Why TestEmacs\* show non-zero seconds in the host e2e suite.** On the host, `requireSandbox` calls `localSandbox.Available()`. Outside the container that runs `hostPreflightOnce.Do(runHostPreflight(...))`, which execs `e2e-sandbox.sh preflight` (Docker calls, bounded at 30s). Every test is `t.Parallel()`, and every TestEmacs\* that reaches the `sync.Once` while the preflight is still running blocks on it. Once it finishes, each one skips via `noteEnvironmentSkipAs`. So the 1 to 5s figures (Register 5.12, CloseWithAHeldPrompt 5.88, ServerSocket 4.51, ...) are each test's share of the wait for one Docker preflight. They are not the test's work, and nothing of the scenario runs. The tests that show 0.0 reached `requireSandbox` after the `Once` had completed. Removing or moving these tests changes the host suite's wall clock only by the preflight overlap (one preflight, a few seconds). The real saving is in the e2e-emacs suite.
- **Every scenario pays for a full world** before it asserts anything: store, sidecar, sidecar build-report wait, Xvfb, Doom boot, daemon spawn, and usually a registered workspace plus an open panel. That holds even for tests that read a static variable (CannotAdoptANamedSession, ConfinesTheServerSocketDirectory, GuiRegistryNamesOnlyLiveCapabilities) or call a pure decoder (UnknownRosterArmIsRefusedLoudly). TestEmacsPrefixAndPostfixSendVariants builds two full worlds, one per subtest.
- **A tier is missing: daemonless Doom-booted GUI Emacs.** ERT runs `emacs -Q`, where `map!` is a no-op stub (stated in test-keybindings.el). So keybinding resolution, Doom popup placement, `+workspaces` recycling, and xwidget teardown can only be observed in this layer today. That is why most G5 rows are MOVE with no target that exists yet. One option is a cheap variant of `NewEmacsWorld` that boots Doom on Xvfb and points Emacs at `lisp/testsupport/fakedaemon` instead of spawning store, sidecar, and daemon. It would let G5 leave the real-daemon world without losing what only a Doom boot can see.
- **Assertions weaker than their names:**
  - OpenProgressLadderReachesRendered passes on `:acked` and never requires `:loaded`.
  - RestartHoldsPromptsMeanwhile never checks that the held deferral survives the restart. Its own comment says it does not read the daemon's held tray.
  - ProofOfLife's step 6 "cross-check the daemon's own frame" only dials the address and asserts nothing about a frame.
  - AdoptsAnAlreadyAnsweringDaemon tests "a second ensure while linked is a no-op", not adoption of a daemon this Emacs did not spawn.
- **Wording that may mislead:** the interrupt file's comments call the test "GRACEFUL restart" while also saying "the restart is immediate: it hard-stops the gated turn". The ERT `verbs-restart-sends-no-force-field` confirms Emacs sends no force flag, so "Forced" in the test names describes daemon behaviour, not an Emacs option.
- **The heartbeat covers wedges globally:** `armHeartbeat`/`declareWedged` in emacs_test.go fails any scenario whose Emacs stops answering. So "does not wedge" tests duplicate a property every scenario checks. They add value only through their specific trigger sequence.
